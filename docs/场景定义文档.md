# lark-dispatch：会后知识智能分发 Agent

## 场景定义文档

---

## 一、问题背景

### 1.1 核心痛点

在企业办公中，会议是知识产生的最高频场景。但会议结束后，决策、待办、知识点往往**只停留在会议纪要文档里**，面临三个断裂：

| 断裂类型 | 具体表现 |
|---------|---------|
| **信息到达断裂** | 会议纪要存到文档/知识库，但相关人不知道、不看、不翻 |
| **责任分配断裂** | 会上口头分配的待办没有变成飞书任务，执行无追踪 |
| **知识沉淀断裂** | 有价值的决策和结论散落在单次会议中，团队无法复用 |

### 1.2 现状：整合做到了，分发没跟上

> 我在开发 lark-retro（基于飞书 CLI 的 AI 回顾工作流）时发现：自动采集日历、会议纪要、任务、消息并生成结构化报告后，报告的交付物是一份飞书文档。
>
> **文档生成了——然后它就死在知识库里了。**
>
> 该看的人不知道有这份文档，知道的人懒得翻，跟自己有关的 action item 石沉大海。
>
> **整合只是第一步，分发才是知识真正产生价值的地方。**

### 1.3 本项目要解决的问题

**一句话**：开完会，AI 自动把决策、待办、知识点分给该知道的人——知识不落地，不散会。

---

## 二、目标用户

### 2.1 主用户：项目负责人 / PM / 团队组长

**用户画像**：
- 每周参加 5-10 场会议
- 需要追踪多个项目的进展和待办
- 最痛的事：会上分配了任务，会后要一个一个手动建任务、手动@人提醒
- 最怕的事：两周后发现某个决策没人执行，因为"没人记得"

**核心诉求**：
- 开完会不用手动整理和分发
- 确保每条待办都有人接、有人追
- 关键决策不丢失、可回溯

### 2.2 次要用户：参会成员

**核心诉求**：
- 会后只收到跟自己有关的信息，不被无关内容打扰
- 待办自动出现在自己的任务列表里，不需要自己去翻纪要

## 三、核心场景与用户故事

### 场景：项目周会结束后

**Before（现状）**：
1. PM 开完周会，会议纪要自动生成（或手动记录）
2. PM 把纪要链接丢到项目群里，说"大家看一下"
3. 3 天后，前端同学说"我不知道设计稿改方案了"
4. 1 周后，PM 发现某个待办根本没人认领
5. 下次周会，花 15 分钟对齐上次的遗留问题

**After（使用 lark-dispatch）**：
1. 周会结束，PM 触发 lark-dispatch（或自动触发）
2. Agent 自动读取会议纪要，AI 提取三类信息：
   - 📋 **待办事项**：识别责任人 → 自动创建飞书任务并分配
   - 📢 **关键决策**：识别相关人 → 私聊/群聊定向推送
   - 📚 **知识要点**：团队级信息 → 自动沉淀到 Wiki / 多维表格
3. Agent 生成**分发报告**：什么信息发给了谁，覆盖率如何
4. 下次周会前，Agent 自动检查上次待办的完成情况

### 用户故事

| 编号 | 作为... | 我想要... | 以便于... |
|------|--------|----------|---------|
| US-1 | PM | 会后自动提取待办并创建飞书任务 | 不再手动分配，确保每条待办有人接 |
| US-2 | PM | 关键决策自动推送给相关人 | 不再依赖"大家自己去看纪要" |
| US-3 | PM | 看到分发报告，知道什么发给了谁 | 确认信息覆盖无遗漏 |
| US-4 | 参会成员 | 只收到跟我有关的待办和决策 | 不被无关信息打扰，专注执行 |
| US-5 | PM | 下次会议前自动检查上次待办完成情况 | 闭环追踪，不再开会对齐旧问题 |

## 五、技术路径

### 5.1 基于飞书 OpenClaw + 飞书 CLI

| 能力 | 实现方式 | 所需权限/Scope | 已知限制 | 验证状态 |
|------|---------|---------------|---------|---------|
| 会议纪要采集 | `minutes get` | `minutes:minute:read` | 仅能读取自己参加的会议纪要 | ✅ lark-retro E2E 验证 |
| 会议录制搜索 | `vc +search` / `vc +notes` | `vc:record:readonly` + `docs:document.content:read` | 需会议开启录制；`note_doc_token` 需二次 fetch | ✅ lark-retro E2E 验证 |
| 日历日程读取 | `calendar +agenda` | `--domain calendar` | 默认读取主日历，跨日历需额外配置 | ✅ lark-retro E2E 验证 |
| 任务创建与分配 | `task +create` | `--domain task` | 分配给他人需对方在同一租户内 | ✅ lark-retro E2E 验证 |
| 任务完成状态检查 | `task +get-my-tasks` / `task +complete` | `--domain task` | 仅能操作自己创建或被分配的任务 | ✅ lark-retro E2E 验证 |
| 消息定向推送 | `im +messages-send --as bot` | Bot 能力 + `im:message:send_as_bot` | **需 bot 身份发送**；私聊需用户先与 bot 有会话 | ✅ lark-retro E2E 验证 |
| Wiki 知识沉淀 | `wiki +node-create` + `docs +create` | `--domain docs` + wiki 空间权限 | 需目标知识库已授权 bot/user 写入 | ✅ lark-retro E2E 验证 |
| 多维表格归档 | `base +record-batch-create` | `--domain base` | 需提供目标 `base_token` / `table_id` | ⚠️ lark-retro 命令验证通过，真实写入需目标表 |
| 联系人/相关人识别 | `contact +search` / `contact +me` | `contact:user.base:readonly` | 搜索结果受通讯录权限范围限制 | 🔲 **待验证** |
| AI 提取+分发路由 | 大模型（飞书 AI / 火山方舟） | 火山方舟 API Token | 提取准确率依赖 prompt 设计和纪要质量 | 🔲 **新增核心能力，待验证** |
| 分发报告生成 | `docs +create` / `docs +update` | `--domain docs` | — | ✅ lark-retro E2E 验证 |

### 5.2 权限降级策略

与 lark-retro 一致，lark-dispatch 采用**渐进式权限**设计：缺少部分 scope 时跳过对应模块并在分发报告中标注，不中断主流程。

| 缺少权限 | 降级行为 |
|---------|---------|
| `minutes:minute:read` | 跳过会议纪要采集，仅从日历/任务等源整合 |
| `vc:record:readonly` | 跳过会议录制内容，仅用纪要摘要 |
| Bot 未配置 | 跳过消息推送，仅创建任务和文档 |
| Wiki 空间未授权 | 知识沉淀降级为创建独立文档 |

### 5.3 与 lark-retro 的关系

- **lark-retro**：解决"知识整合"——从多数据源自动采集，生成结构化报告
- **lark-dispatch**：解决"知识分发"——把整合后的知识按人、按类型精准送达
- **核心新增**：AI 分析层（提取三类信息 + 识别相关人 + 分发路由逻辑）

## 六、MVP 范围定义

### 6.1 MVP 包含（Must Have）

- [ ] 读取一场会议的纪要内容
- [ ] AI 提取：待办事项（含责任人）、关键决策（含相关人）、知识要点
- [ ] **提取结果展示给用户确认/编辑后再执行分发**（AI 辅助决策，人类拍板执行）
- [ ] 待办 → 经确认后自动创建飞书任务并分配给责任人
- [ ] 决策 → 经确认后通过飞书消息推送给相关人
- [ ] 知识 → 经确认后沉淀到 Wiki 文档
- [ ] 生成分发报告：什么信息发给了谁

### 6.2 增强功能（Nice to Have，时间允许再做）

- [ ] 下次会议前自动检查上次待办完成状态
- [ ] 多维表格归档分发记录
- [ ] 支持批量处理多场会议

### 6.3 不做（Out of Scope）

- 实时会议监听（需要额外权限和技术栈）
- 自定义分发规则引擎（MVP 阶段 AI 自动判断即可）
- 跨组织分发

## 七、效果验证思路

### 7.1 验证维度

| 维度 | 指标 | 验证方法 |
|------|------|---------|
| **信息到达率** | 待办/决策是否到达了正确的人 | 对比人工分发 vs Agent 分发的覆盖率 |
| **效率提升** | 会后整理+分发耗时 | 对比手动操作 vs Agent 自动化的时间 |
| **准确率** | AI 提取的待办/决策/知识是否正确 | 人工核验 AI 提取结果的准确率 |
| **闭环率** | 被分发的待办是否被执行 | 追踪任务完成情况 |

### 7.2 验证方案

1. 准备 3-5 份真实或模拟的会议纪要
2. 分别用手动方式和 lark-dispatch 处理
3. 对比效率、准确率、覆盖率数据
4. 输出效果验证报告
